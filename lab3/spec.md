## 2. Відповідність UC до сценаріїв

### UC-01. Переглянути каталог задач
- Учасники: Гість, Система
- Мета: переглянути доступні задачі та їх основні характеристики.

Сценарії:
- SC-01. Фільтрація задач за складністю та тегом
  - Учасники: Гість, Система
  - Кроки:
    1. Гість відкриває каталог задач.
    2. Вибирає складність "Easy" та тег "Array".
    3. Система показує лише задачі, що відповідають критеріям.
    4. Для кожної задачі відображаються назва, складність і теги.

- SC-02. Розв'язана задача позначена в каталозі
  - Учасники: Користувач, Система
  - Кроки:
    1. Користувач авторизований.
    2. У користувача є Accepted submission для задачі "Two Sum".
    3. Користувач відкриває каталог.
    4. Система позначає "Two Sum" як розв'язану.
    5. Інша задача без Accepted submission залишається не позначеною.

### UC-02. Фільтрувати задачі
- Учасники: Гість, Система
- Мета: звузити список задач за заданими параметрами.

Сценарії:
- SC-01. Фільтрація задач за складністю та тегом
  - Учасники: Гість, Система
  - Кроки:
    1. Гість задає фільтр за складністю та тегом.
    2. Система перевіряє відповідність задач критеріям.
    3. На екрані показуються лише задачі, що проходять фільтрацію.
    4. Відображаються назва, складність і теги задачі.

### UC-03. Зареєструватися
- Учасники: Гість, Система
- Мета: створити новий обліковий запис користувача.

Сценарії:
- SC-03. Успішна реєстрація
  - Учасники: Гість, Система
  - Кроки:
    1. Гість вводить username, email і пароль.
    2. Система перевіряє, що username і email вільні.
    3. Система створює нового користувача з role = user.
    4. У базі зберігається хеш пароля.

- SC-04. Реєстрація з уже зайнятим email
  - Учасники: Гість, Система
  - Кроки:
    1. Гість вводить email, який уже існує в системі.
    2. Система виявляє конфлікт.
    3. Реєстрацію відхиляють.
    4. Система повідомляє про зайнятий email.
    5. Новий користувач не створюється.

### UC-04. Увійти за email і паролем
- Учасники: Гість, Система
- Мета: авторизувати користувача через його облікові дані.

Сценарії:
- SC-05. Успішний вхід за email і паролем
  - Учасники: Гість, Система
  - Кроки:
    1. Гість вводить email і пароль.
    2. Система перевіряє відповідність даних користувача.
    3. Система авторизує користувача в системі.

- SC-06. Вхід з неправильним паролем
  - Учасники: Гість, Система
  - Кроки:
    1. Гість вводить правильний email, але неправильний пароль.
    2. Система перевіряє дані та виявляє невідповідність.
    3. Вхід відхиляється.
    4. Система показує повідомлення про помилку.
    5. Користувач залишається неавторизованим.

### UC-05. Надіслати рішення
- Учасники: Користувач, Система
- Мета: надіслати рішення задачі мовою програмування для перевірки.

Сценарії:
- SC-07. Правильне рішення отримує статус Accepted
  - Учасники: Користувач, Система
  - Кроки:
    1. Користувач обирає мову програмування.
    2. Надсилає рішення для задачі.
    3. Система створює submission зі статусом Pending.
    4. Після перевірки рішення проходить всі тест-кейси.
    5. Submission змінюється на Accepted.
    6. Система фіксує runtime та memory.
    7. Завершене правильне рішення зберігається в історії користувача.

- SC-08. Рішення перевищує ліміт часу
  - Учасники: Користувач, Система
  - Кроки:
    1. Користувач надсилає рішення.
    2. Один з тестів виконується довше встановленого ліміту.
    3. Система зупиняє перевірку.
    4. Рішення не зберігається як Accepted submission.
    5. Користувачу показується помилка перевищення ліміту часу.

### UC-06. Перевірити рішення на тест-кейсах
- Учасники: Система, Користувач
- Мета: автоматично перевірити рішення на тестових даних.

Сценарії:
- SC-07. Правильне рішення отримує статус Accepted
  - Учасники: Система, Користувач
  - Кроки:
    1. Система запускає перевірку на наборі тест-кейсів.
    2. Всі тести проходять.
    3. Система встановлює статус Accepted.
    4. Результат зберігається як валідне рішення користувача.

- SC-08. Рішення перевищує ліміт часу
  - Учасники: Система, Користувач
  - Кроки:
    1. Система запускає виконання рішення.
    2. Один з тестів перевищує ліміт часу.
    3. Система зупиняє перевірку та фіксує помилку.
    4. Невдале виконання не записується як Accepted submission.

### UC-07. Переглянути історію правильних рішень
- Учасники: Користувач, Система
- Мета: переглянути власні прийняті рішення.

Сценарії:
- SC-09. Перегляд історії правильних рішень
  - Учасники: Користувач, Система
  - Кроки:
    1. Користувач відкриває історію надсилань.
    2. Система показує лише його власні Accepted submission.
    3. Показані записи сортуються за датою (найновіші перші).
    4. Для кожного submission відображаються статус, мова, runtime та дата.

- SC-23. Складність видно в історії надсилань
  - Учасники: Користувач, Система
  - Кроки:
    1. Користувач відкриває історію надсилань.
    2. Для Accepted submission показують time_complexity та space_complexity.

### UC-08. Опублікувати рішення задачі
- Учасники: Користувач, Система
- Мета: опублікувати пояснення до прийнятого рішення.

Сценарії:
- SC-10. Успішна публікація рішення
  - Учасники: Користувач, Система
  - Кроки:
    1. Користувач має Accepted submission до задачі.
    2. Користувач створює пост на його основі.
    3. Система перевіряє, що submission прийнято і у нього ще немає розбору.
    4. Створюється EditorialPost із назвою, прив'язкою до задачі та користувача.

### UC-09. Оформити Premium
- Учасники: Користувач, Платіжний сервіс, Система
- Мета: активувати Premium або оплатити підписку.
- Примітка: подарунковий Premium є частиною цього UC, а не окремим незалежним use case.

Сценарії:
- SC-11. Успішна оплата Premium собі
  - Учасники: Користувач, Платіжний сервіс, Система
  - Кроки:
    1. Користувач ініціює оформлення Premium для себе.
    2. Платіжний сервіс підтверджує оплату.
    3. Система встановлює has_premium = true.

- SC-12. Успішне оформлення Premium у подарунок
  - Учасники: Користувач, Платіжний сервіс, Система
  - Кроки:
    1. Користувач оформлює Premium для іншого користувача.
    2. Платіжний сервіс підтверджує оплату.
    3. Система надає Premium одержувачу.
    4. У користувача, який купив подарунок, Premium не активується.

- SC-13. Відмова в оплаті Premium (первинна)
  - Учасники: Користувач, Платіжний сервіс, Система
  - Кроки:
    1. Користувач починає оплату Premium.
    2. Платіжний сервіс повертає помилку: "Недостатньо коштів".
    3. Система залишає has_premium = false.
    4. Користувачу показують причину відмови.

- SC-14. Відмова при поновленні Premium — підписка залишається активною
  - Учасники: Користувач, Платіжний сервіс, Система
  - Кроки:
    1. Користувач вже має активний Premium.
    2. Під час автоматичного списання платіжний сервіс відмовляє.
    3. Система зберігає дату невдалої оплати.
    4. Premium залишають активним.

- SC-15. Premium скасовується через тиждень неоплати
  - Учасники: Система, Користувач, Платіжний сервіс
  - Кроки:
    1. У користувача є активний Premium.
    2. Система перевіряє стан підписки.
    3. Після 7 днів без успішної оплати підписку анулюють.
    4. has_premium стає false.

- SC-18. Подарунок неіснуючому користувачу
  - Учасники: Користувач, Система
  - Кроки:
    1. Користувач намагається подарувати Premium неіснуючому користувачу.
    2. Система перевіряє наявність користувача.
    3. Операцію відхиляють.
    4. Запит до платіжного сервісу не надсилається.

- SC-19. Подарунок користувачу, який уже має Premium
  - Учасники: Користувач, Система
  - Кроки:
    1. Користувач пробує подарувати Premium користувачу, який уже має Premium.
    2. Система перевіряє статус одержувача.
    3. Операцію відхиляють.
    4. Система повідомляє, що Premium вже активний.

### UC-10. Відкрити Premium-задачу
- Учасники: Користувач, Premium-користувач, Система
- Мета: перевірити доступ до платних задач залежно від статусу Premium.

Сценарії:
- SC-16. Користувач без Premium відкриває Premium-задачу
  - Учасники: Користувач, Система
  - Кроки:
    1. Користувач без Premium відкриває Premium-задачу.
    2. Задача відображається в каталозі.
    3. Опис задачі та форма надсилання заблоковані.

- SC-17. Premium-користувач відкриває Premium-задачу
  - Учасники: Premium-користувач, Система
  - Кроки:
    1. Premium-користувач відкриває Premium-задачу.
    2. Система показує опис задачі.
    3. Система надає доступ до форми відправки рішення.

### UC-11. Створити задачу
- Учасники: Адміністратор, Користувач, Система
- Мета: додати нову задачу з перевірочними даними.

Сценарії:
- SC-20. Збереження задачі без тест-кейсів
  - Учасники: Адміністратор, Система
  - Кроки:
    1. Адміністратор намагається створити задачу без жодного тест-кейсу.
    2. Система перевіряє валідацію.
    3. Збереження відхиляється.
    4. Задача не з'являється в каталозі.

- SC-21. Користувач без ролі admin створює задачу
  - Учасники: Користувач, Система
  - Кроки:
    1. Користувач без ролі admin намагається створити задачу.
    2. Система перевіряє права доступу.
    3. Дію відхиляють.
    4. Задача не з'являється в каталозі.

### UC-12. Обчислити time та space complexity
- Учасники: Система, Користувач
- Мета: визначити асимптотичну складність прийнятого рішення.

Сценарії:
- SC-22. Підрахунок time та space complexity після Accepted
  - Учасники: Користувач, Система
  - Кроки:
    1. Користувач надсилає прийняте рішення.
    2. Система перевіряє, що рішення Accepted.
    3. Система обчислює time_complexity та space_complexity.
    4. Результат відображається у submission і в історії надсилань.

- SC-23. Складність видно в історії надсилань
  - Учасники: Користувач, Система
  - Кроки:
    1. Користувач відкриває історію надсилань.
    2. Для Accepted submission система показує time_complexity і space_complexity.
