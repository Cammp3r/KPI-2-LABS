# Аудит - Завдання 4: Activity-діаграма

## 1. Перевірка відповідності формі та вимогам

| Перевірка | Результат |
|---|---|
| Одна декларативна форма | + Використано лише Mermaid `flowchart TD`, без змішування з sequence/BPMN |
| Початок і кінець процесу | + Є `Start` і спільний `End` для успішної, помилкової та невалідної гілок |
| Розгалуження | + Перевіряється валідність запиту, результат виконання та наявність наступних тестів |
| Цикл | + Після успішного тесту Judge повертається до завантаження наступного тест-кейсу |
| Fork/join | + Після `Accepted` паралельно обчислюються time complexity і space complexity; `Join` очікує обидві гілки |
| Ролі / swimlanes | + Окремо показані Client, System, Judge, CodeRunner і ResourceMonitor |
| Надсилання повідомлення | + Показано `executeTestCase` від Judge до CodeRunner і `testResult` назад |
| Поведінка без очікування | + `submissionQueued` показується у Web UI, після чого UI не очікує завершення Judge |

## 2. Повнота переходів і досяжність

- Із `Start` досяжні всі дії користувача, перевірка запиту та створення
  `Submission` зі статусом `Pending`.
- Невалідний запит завершується повідомленням про помилку без запуску Judge.
- Валідний запит передає submission до Judge і має окреме повідомлення
  `submissionQueued`; це пояснює асинхронне продовження процесу.
- Для кожного тест-кейсу є повний ланцюг `executeTestCase` → виконання в sandbox
  → `testResult` і метрики → перевірка Judge.
- Гілки `Compilation Error`, `Runtime Error`, `Time Limit Exceeded` і
  `Wrong Answer` зберігають фінальний статус і показують результат користувачу.
- Гілка `test passed` або повертається до наступного тесту, або переходить до
  `Accepted`. Успішний шлях проходить через fork/join і також завершується.

## 3. Перевірка умов і повідомлень

| Повідомлення | Відправник → отримувач | Подальша поведінка |
|---|---|---|
| `submissionQueued` | System → Web UI | UI показує Pending і не блокує користувача очікуванням Judge |
| `executeTestCase(code, testCase)` | Judge → CodeRunner | CodeRunner приймає подію, запускає код в ізольованому sandbox |
| `testResult` | CodeRunner → Judge | Judge перевіряє вивід, runtime і ліміт 2000 мс |
| execution metrics | ResourceMonitor → Judge | Judge використовує runtime/memory для результату; для Accepted вони зберігаються |
| final result | System → Web UI | UI показує статус, а для помилки - деталі першого невдалого тесту |

Якщо `submissionQueued` не очікує відповіді від Judge, UI продовжує роботу,
а перевірка виконується асинхронно. Для `executeTestCase` діаграма показує
нормальну відповідь `testResult`; окремий транспортний timeout не входить до
UC-05 і не ототожнюється з `Time Limit Exceeded`, бо цей статус означає саме
перевищення 2000 мс виконання користувацького коду.

## Висновок

Поточна activity-діаграма має досяжні завершальні шляхи, явний цикл,
розгалуження, fork/join, swimlanes і повідомлення між учасниками. Вона
деталізує UC-05 і узгоджує процес із вимогами lab2 та основними повідомленнями
sequence-діаграм lab3.
