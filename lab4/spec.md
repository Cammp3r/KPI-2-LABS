# Процес - UC-05 Надіслати рішення

## 1. Призначення

Цей документ деталізує use case **UC-05 «Надіслати рішення»** із Завдання 2
для LeetCode-подібної платформи. Процес описує надсилання коду користувачем,
його постановку в чергу, виконання в ізольованому середовищі та повернення
фінального вердикту.

Деталізація охоплює два сценарії із Завдання 3:

- **SC-07** - правильне рішення отримує статус `Accepted`;
- **SC-08** - рішення перевищує ліміт часу й отримує статус
  `Time Limit Exceeded`.

## 2. Межі та учасники

### Основний актор

**Користувач** - автор рішення, який обирає задачу, мову програмування та
надсилає код.

### Компоненти системи

| Учасник | Відповідальність у процесі |
|---|---|
| Web UI | показує форму надсилання, приймає дані та відображає результат |
| SubmissionController | приймає запит від UI і запускає перевірку |
| SubmissionService | створює `Submission`, змінює статус і зберігає результат |
| Judge | керує перевіркою рішення на всіх тест-кейсах |
| CodeRunner | виконує код у sandbox для одного тест-кейсу |
| ResourceMonitor | вимірює час і використану пам'ять |
| База даних | зберігає задачі, тест-кейси, `Submission` та історію користувача |

У зовнішні платіжні або інші сервіси процес не звертається. Ізоляція
виконання коду є внутрішньою відповідальністю `CodeRunner` і в цій
специфікації показана як один крок.

## 3. Передумови та результат

### Передумови

1. Користувач авторизований.
2. Обрана задача існує та доступна користувачу.
3. Обрана мова є записом у таблиці `Language`.
4. Для задачі існує щонайменше один `TestCase`.
5. Користувач надав непорожній програмний код.

### Гарантований результат

- Система створює `Submission` зі статусом `Pending`, мовою, задачею та часом
  надсилання.
- Після завершення перевірки `Submission` має рівно один фінальний статус:
  `Accepted`, `Wrong Answer`, `Time Limit Exceeded`, `Runtime Error` або
  `Compilation Error`.
- Для `Accepted` система зберігає `runtime_ms` і `memory_kb`, додає рішення
  до історії користувача та може обчислити оцінки складності.
- Для нефінального результату `Accepted` оцінки `time_complexity` і
  `space_complexity` не обчислюються.

## 4. Основний потік подій

| № | Роль / компонент | Дія та повідомлення |
|---:|---|---|
| 1 | Користувач | Відкриває форму надсилання задачі. |
| 2 | Web UI | Показує доступні мови з `Language`. |
| 3 | Користувач | Обирає мову та вводить код. |
| 4 | Користувач → Web UI | Надсилає `submitSolution(code, languageID, problemID)`. |
| 5 | Web UI → SubmissionController | Передає код, мову, задачу та `userID`. |
| 6 | SubmissionController | Перевіряє авторизацію, наявність задачі, мови та непорожній код. |
| 7 | SubmissionController → SubmissionService | Викликає `createPendingSubmission(...)`. |
| 8 | SubmissionService → База даних | Створює `Submission` зі статусом `Pending` і `submitted_at`. |
| 9 | База даних → Web UI | Повертає `submissionID`; UI показує повідомлення `submissionQueued`. |
| 10 | SubmissionController → Judge | Запускає `validateSubmission(submissionID)`. |
| 11 | Judge → База даних | Завантажує тест-кейси задачі по одному. |
| 12 | Judge → CodeRunner | Для кожного тесту передає код і вхідні дані через `executeTestCase`. |
| 13 | CodeRunner → ResourceMonitor | Передає вимірювання часу та пам'яті. |
| 14 | Judge | Порівнює фактичний результат з очікуваним і перевіряє ліміти. |
| 15 | Judge → SubmissionService | Якщо всі тести пройдені, викликає `markAsAccepted`. |
| 16 | SubmissionService → База даних | Записує `Accepted`, `runtime_ms`, `memory_kb` та історію користувача. |
| 17 | SubmissionController → Web UI | Надсилає `displayResults("Accepted", runtime, memory)`. |
| 18 | Web UI → Користувач | Показує успішний вердикт і метрики виконання. |

## 5. Розгалуження та повідомлення про помилки

| Умова | Дії системи | Повідомлення користувачу |
|---|---|---|
| Дані запиту невалідні | Не створює `Submission`, повертає помилку валідації | «Оберіть мову та введіть код» |
| Задача або мова не існує / недоступна | Не запускає виконання | «Задачу або мову не знайдено» |
| Помилка компіляції | Зупиняє перевірку, встановлює `Compilation Error` | Помилка компіляції |
| Фактичний результат не збігається з очікуваним | Зупиняє перевірку, встановлює `Wrong Answer` | Показує перший непройдений тест, очікуваний і фактичний вивід |
| Виконання триває понад 2000 мс | `CodeRunner` зупиняє виконання, Judge встановлює `Time Limit Exceeded` | «Перевищено ліміт часу» |
| Код завершується з помилкою | Зупиняє перевірку, встановлює `Runtime Error` | Повідомлення про помилку виконання |
| Усі тест-кейси пройдено | Встановлює `Accepted`, зберігає метрики та історію | «Рішення прийнято» з `runtime` і `memory` |

Для кожної гілки з фінальним статусом, відмінним від `Accepted`, система
зберігає цей статус у тому самому `Submission`; таке рішення не позначається
як прийняте.

## 6. Обрана форма

Обрана форма - **activity diagram зі swimlanes**. Вона відповідає характеру
UC-05, оскільки процес має чітку часову послідовність, повторення для кожного
тест-кейсу, передачу повідомлень між ролями та кілька взаємовиключних
розгалужень. Машина станів була б доречнішою для життєвого циклу
`Submission`, а BPMN - для процесу з організаційними подіями та зовнішніми
учасниками, яких у цьому UC немає.
