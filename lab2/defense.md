DEFENSE — Завдання 2: Вимоги та Use Cases

Намір і критерії (1–2 речення):
Намір: Формалізувати вимоги та use cases для платформи LeetCode у вигляді EARS-вимог, user stories та Gherkin-сценаріїв, пов'язаних матрицею трасування.

Критерії: Вимоги мають бути однозначними й тестовними (EARS), трасування - реально багато-до-багатьох з позначеними непокритими елементами, use-case діаграма - містити більше 2-ох типів акторів, include/extend та узагальнення, а актори й сутності - узгоджені з моделлю даних із Завдання 1.

Топ-3 розбіжності (spec ↔ артефакт) + коміт-виправлення:
### №1. Subscription - `USER.has_premium`
- **Знайдено:** spec містила сутність Subscription, якої немає в моделі; Premium у моделі - булеве поле `USER.has_premium`.
- **Виправлення:** Subscription прибрано зі spec; платіжний сервіс змінює `has_premium`.
- **Коміт:** `https://github.com/Cammp3r/KPI-2-LABS/commit/520d653557a4d1e6d80b3a8cac6e4e29d6a620d7`

### №2. Фільтр за мовою програмування
- **Знайдено:** перша версія сценаріїв фільтрувала задачі за мовою, але в моделі `Problem` не має мови, і вимоги такого фільтра немає.
- **Виправлення:** фільтрація лише за складністю й тегом.
- **Коміт:** `https://github.com/Cammp3r/KPI-2-LABS/commit/ac1b22440c3693773b76214a7de3ee28771f79d3`

### №3. Помилка в spec
- **Знайдено:** в spec не було написано що користувач може купити преміум підписку.
- **Виправлення:** spec виправлено.
- **Коміт:** `https://github.com/Cammp3r/KPI-2-LABS/commit/9aa929017bbaffd41925ca0ea447f23161b3e351`

Ключове рішення - які альтернативи зважив і чому обрав цю (ADR):
1. Проблема: Яким EARS-шаблоном описати блокування доступу до Premium-задач для користувача без підписки (`has_premium = false`).
- Альтернатива: Шаблон WHERE (WHERE `has_premium = false`, система SHALL блокувати доступ...). Відкинуто: WHERE призначений для опціональних можливостей продукту (production features), а не для стану конкретного користувача.
- Обране рішення: Шаблон WHILE (WHILE у користувача `has_premium = false`, система SHALL показувати задачі та блокувати опис і надсилання рішень) - точніше відображає поведінку.

## Зміни: грейс-період при неоплаті поновлення Premium

**Що попросили:** при першій відмові в оплаті (ще немає Premium) доступ не надавати; якщо Premium уже був і не вдалось списати кошти за наступний місяць — не забирати підписку одразу, а лише через тиждень після невдалої оплати.

**Що змінено:**
- **requirements.md**: REQ-17 звужено до первинної відмови (ще немає Premium); додано REQ-18 (відмова при щомісячному поновленні — `has_premium` лишається `true`, зберігається дата невдалої оплати `premium_payment_failed_at`) і REQ-19 (через 7 днів без оплати — `has_premium = false`). Решту вимог Premium/Адміністрування перенумеровано (REQ-20…REQ-25).
- **scenaries.md**: додано SC-16 (відмова при поновленні — підписка активна) і SC-17 (скасування через тиждень); також повернув SC-13 "Успішна оплата Premium собі" — цей сценарій зник при додаванні подарунка, хоча REQ-16 описує і самостійну оплату теж. Сценарії подарунка (SC-20, SC-21) переніс з Rule "Адміністрування" в Rule "Premium" — вони туди й належать. Решту сценаріїв перенумеровано (SC-01…SC-23 суцільно).
- **traceability.md**: усі таблиці перебудовано під нову нумерацію; у "Перевірка багато-до-багатьох" додав UC-12 (раніше випав, хоча має 3 сценарії).
- **audit.md**: оновив номери REQ у таблиці EARS; додав відкрите питання — для грейс-періоду потрібне нове поле `USER.premium_payment_failed_at`, якого немає в ER-моделі Завдання 1 (за межі цього lab не виходив, lab1 не чіпав).
- **spec.md, usecase.puml, stories.md**: без змін — нова логіка це продовження існуючого UC-09 "Оформити Premium", новий use case не потрібен.
