# Специфікація — Завдання 2: Вимоги та Use Cases (LeetCode-подібна платформа)

## Актори та головні цілі

| Актор | Тип | Головні цілі |
|---|---|---|
| Гість | людина | переглядати список задач, зареєструватися або увійти |
| Користувач | людина (узагальнює Гостя) | розв'язувати задачі, надсилати рішення, бачити вердикт та історію надсилань |
| Premium-користувач | людина (узагальнює Користувача) | відкривати Premium-задачі та офіційні розв'язки |
| Автор задач | людина | створювати й редагувати задачі та їхні тест-кейси |
| Платіжний сервіс | зовнішня система | проводити оплату підписки й повідомляти платформу про результат |
| OAuth-провайдер | зовнішня система | автентифікувати користувача через GitHub / Google |

## Сутності (з моделі даних Завдання 1)
User, Problem, TestCase, Submission, Subscription.
> Назви й атрибути мають збігатися з моделлю Завдання 1; будь-яка розбіжність фіксується в аудиті.

## Межі
**Входить:** реєстрація та вхід (зокрема через OAuth), перегляд задач, надсилання рішення й отримання вердикту, історія надсилань, оформлення Premium-підписки, керування задачами та тест-кейсами.
**Не входить:** контести, рейтинги, форум / обговорення, внутрішня реалізація ізоляції коду (sandbox).

## Критерії прийняття
1. Є ≥2 типи акторів: людина та зовнішня система.
2. Кожна вимога записана за шаблоном EARS, має ID `REQ-xx`, не містить неперевірних слів («швидко», «зручно», «коректно») і задає конкретні умови або числові межі.
3. Кожна user story має ≥1 Gherkin-сценарій (Given/When/Then).
4. Матриця трасування є багато-до-багатьох: хоча б одна вимога покрита ≥2 сценаріями і хоча б один сценарій покриває ≥2 вимоги.
5. У матриці є ≥1 непокрита вимога або UC з поясненням, чому її не покрито.
6. Use-case-діаграма (PlantUML) містить ≥2 типи акторів, ≥1 `include`, ≥1 `extend` та ≥1 узагальнення.
7. Усі актори та сутності з вимог і сценаріїв присутні в моделі даних Завдання 1, або розбіжність описана в аудиті.
8. Топ-3 розбіжності виправлено через зміну spec або критеріїв, кожну окремим комітом.
